## 2. AthleteSourceAccount canonical status

`AthleteSourceAccount` is the **single source of truth** for per-athlete connection state:

- Unique `(athlete_id, source)`; `SourceProvider` contract receives an `AthleteSourceAccount` in every method.
- Holds auth (`auth_json`, `auth_status`), sync cursor (`cursor_json`), health (`health`, `blocked_until`, `last_success_at`, `last_error_at`, `consecutive_failures`), and optional `platform_id` / `device_id`.
- `SourceState` docstring now says explicitly `DEPRECATED` with removal plan.
- New test `test_source_state_is_deprecated_and_unreferenced` fails if any file in `src/trailcoach/` (other than `models.py`) references `SourceState`, preventing a second source of truth from creeping in.

## 3. Migration strategy decision

**Decision: introduce Alembic now.**

Rationale:
- P0.1 writes the first real, non-reproducible data (Garmin FIT imports, wellness, dedup reviews). Once that DB exists, any schema change without a migration tool means `drop_all` + re-import, which is exactly the situation the raw-data-first principle is supposed to avoid.
- `alembic>=1.13.0` was already declared in `pyproject.toml`; the cost is only configuration.
- `create_all` cannot express column adds/renames, constraint changes or data migrations; the P0.0 `WellnessDaily` PK change would already have been impossible on a live DB.
- Having a baseline *before* Garmin means the first Garmin-related schema change (if any) is a normal incremental revision, not a retroactive baseline.

`Base.metadata.create_all` is retained only inside tests (fresh in-memory DB per test) — this is standard practice and not a second migration path.

## 5. Dedup vs Source-of-Truth analysis

Two responsibilities, now explicitly separated:

**A. Deduplication — "are these the same activity?"**
- `DedupeEngine.evaluate()` computes `time_score`, `distance_score`, `duration_score`, `source_bonus` → `final_score` → `AUTO_LINK / REVIEW / SEPARATE`.
- `source_bonus` reads **only** `SourcePriority(metric="activity")` via `_priority_map`. Its range is `[-0.05, +0.10]` and its weight is `0.15`, so it can shift `final_score` by at most ±0.015 — a tie-breaker, never decisive. It never decides which values are kept.

**B. Source of truth — "which source provides metric X?"**
- New helper `trailcoach.sources.priority.resolve_source_for_metric(db, athlete_id, metric, available_sources)` reads `SourcePriority` for that specific metric and returns the highest-ranked available source; unknown sources fall back to input order.
- It has no knowledge of dedup scores, and `DedupeEngine` has no knowledge of it.

Ambiguity found and resolved: before hardening there was no code path for B — `SourcePriority` was only consumed by the dedup engine, so a reader could infer that the "activity" priority governs all metrics. The helper makes B a first-class, metric-scoped operation.

Tests added:
- `test_dedup_source_bonus_isolated_from_metric_priority`: an `hrv` priority list ranking `source_a > source_b` yields `source_bonus == 0.0` in activity dedup — metric priorities do not leak into dedup.
- `test_resolve_source_for_metric_uses_priority_list`: per-metric winner selection, skipping unavailable higher-ranked sources, and fallback for unknown sources.
