## 2. Bugs found on real data and fixed (parser only)

1. **Unknown sport enum crashes parser** — Garmin "Health Snapshot" files carry `sport=60`,
   which `fitdecode` returns as a raw `int`; `_sport_from_fit` called `.lower()` → 3 files failed.
   Fix: coerce to `str`; numeric codes map to `sport="other"`, `sub_sport="fit_sport_<n>"`.
2. **Cadence units** — FIT `cadence` for foot sports is per-leg (rpm). Stored as `cadence_spm`
   it read 57–85 for runs. Fix: `spm = 2 × (cadence + fractional_cadence)` for
   running/trail_running/walking/hiking; cycling unchanged. Real result: running avg 147 spm,
   trail 136 spm (plausible).
3. **Local time / timezone lost** — `start_time_local` was a copy of UTC and `tz` was NULL.
   Fix: read `activity.local_timestamp − activity.timestamp` → `utc_offset_s`, store
   `start_time_local` (device wall clock) and `tz` as `UTC±HH:MM`. Real result:
   UTC-03:00 ×95, UTC-04:00 ×91, UTC-05:00 ×12 (DST + travel handled per file).

`FitParser.VERSION` bumped 0.2 → 0.3. Tests: 40 passed (2 new), ruff + mypy clean.

## 3. Architecture findings (NOT changed — need decision)

- **F1 · Daily bucketing uses UTC date.** `training/engine.py` and `api/main.py` group with
  `func.date(Activity.start_time_utc)`. On real data **16/198 activities (8 %)** fall on a
  different calendar day in UTC than locally (evening sessions at UTC-3/-4). `daily_load`,
  PMC and weekly views are therefore shifted for those days. Now that `start_time_local` is
  populated, switching the engine to local date is a small change — recommend doing it before
  AI Coach consumes daily state.
  **RESOLVED (commit after `2187e63`)**: `training/engine.py` and `/v1/activities` now bucket by
  `activity_day()` = `date(coalesce(start_time_local, start_time_utc))`. Re-run on real data:
  171 → 173 `daily_load` days, 28 daily rows changed, 16 activities moved to their local day.
  Regression test `test_daily_load_groups_by_local_calendar_day` (41 tests total).
- **F2 · Loads require thresholds.** With no `athlete_threshold` rows, `recalculate` produces
  0 `activity_load` silently. Expected by design, but the CLI should warn. Placeholder
  thresholds were used only for this validation (lthr 165, hr_max 190, rest 50, ftp_pace 3.3).
  **RESOLVED**: `recalculate_athlete` now returns `activities_without_load` and
  `missing_threshold_kinds`; the CLI prints an `AVISO` to stderr. Real DB without thresholds →
  `198 actividades sin carga`; with the placeholders → 0 (only `ftp_power_w` missing).
- **F3 · `total_moving_time` is NULL** in FR955 session messages; `duration_moving_s` falls
  back to `total_timer_time` (pauses excluded, correct enough).
- **F4 · Rich messages ignored** (`time_in_zone`, `split`, `gps_metadata`, `hrv`, `training_effect`,
  `training_stress_score`, `total_calories`). Raw file is preserved, so these can be extracted
  later by a parser version bump + reprocess without re-import.
- **F5 · Dedup calibration.** Single source → 0 REVIEW/AUTO_LINK in the import itself, so the
  198 real activities were used as ground truth against a *simulated* second source
  (`source_b` clones with realistic noise) plus the real neighbouring-activity pairs as
  negatives. Old engine: a perfect match scored exactly 0.85 (weights summed to 0.85 without a
  source bonus) and any activity without distance capped at 0.60.

  | Scenario (198 pairs each) | before | after |
  |---|---|---|
  | Same FIT synced to another platform (Δ=0) | 195 AUTO_LINK / 3 SEPARATE | 198 AUTO_LINK |
  | Second device: ±20 s, ±2 % dist, ±1 % dur | 195 REVIEW / 3 SEPARATE | 198 AUTO_LINK |
  | Phone started 30–120 s late, 1–5 % shorter | 133 SEPARATE / 65 REVIEW | 111 REVIEW / 64 SEPARATE / 23 AUTO_LINK |
  | Real distinct neighbours (2 pairs ≤10 min) | 2 SEPARATE | 2 SEPARATE |

  **RESOLVED**: `DedupeEngine` now renormalizes time/distance/duration weights over the
  components both records carry (zero/NULL distance or duration is "not comparable", not
  "different"), so a perfect match = 1.0; `source_bonus` stays an additive tiebreaker
  (max ±0.015, provably smaller than the REVIEW band). `review_threshold` 0.70 → 0.75.
  Tests: 3 new in P0.0 suite, orchestrator REVIEW fixture made genuinely ambiguous (44 total).
