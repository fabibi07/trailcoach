## 2. SCHEMA_CHANGES

### New tables

| Table | Purpose |
|-------|---------|
| `platform` | Generic platform metadata (`slug`, `name`, `kind`, `is_aggregator`). |
| `device` | Physical devices per athlete (`serial_number`, `manufacturer`, `model`, `name`, `first_seen_at`). |
| `athlete_source_account` | Per-athlete, per-source account and state (`source`, `platform_id`, `device_id`, `auth_json`, `cursor_json`, health/auth/sync timestamps, consecutive failures). Unique on `(athlete_id, source)`. |
| `metric_capability` | Capability matrix per `(source, metric)` with `availability` (`native`/`derived`/`estimated`/`unavailable`) and confidence base. |
| `source_priority` | Ordered source preference list per `(athlete_id, metric)` stored as JSON array. |

### Modified tables

| Table | Change |
|-------|--------|
| `wellness_daily` | `source` promoted from nullable text to part of the primary key `(athlete_id, date, source)`. Added `data_quality`, `quality_flags`, `provenance` JSON and `account_id` FK. This allows multiple wellness sources for the same athlete/day without overwriting. |
| `source_activity` | Added `account_id` FK, `device_id` FK and `provenance` JSON for full lineage. |
| `source_state` | Refactored from a global singleton keyed only by `source` to a per-athlete table keyed by `(athlete_id, source)`. Marked as backward-compatibility layer; new code uses `athlete_source_account`. |
| `dedupe_review` | Added `final_score` (Numeric) to persist the engine score for ambiguous matches. |

### Migrations

The project currently uses `Base.metadata.create_all` in `trailcoach.db.init_db.py`. No Alembic directory or migration runner exists. Schema changes are therefore applied through the existing create-all mechanism.

## 5. SOURCE_PROVIDER

Implemented in `src/trailcoach/sources/provider.py`.

Abstract contract (`SourceProvider`):

| Method | Purpose |
|--------|---------|
| `authenticate` | Validate/refresh credentials; file-based sources return no-op status. |
| `discover_capabilities` | Return `MetricCapability` list for the account. |
| `get_historical_range` | Return `HistoricalRange(start, end)`. |
| `initial_import` | Return `ImportResult` with source activities, canonical activities, wellness, raw files and capabilities. |
| `incremental_sync` | Return `ImportResult` scoped to the account cursor. |
| `download_activity_file` | Return raw bytes of an activity file, or `None`. |
| `get_wellness` | Return `WellnessDaily` records for a date range. |

`MockSourceProvider` in `src/trailcoach/sources/mock.py` validates the contract with synthetic data and never calls an external API. It is registered in `SourceProviderRegistry` under the slug `mock`.

## 6. MULTI_SOURCE_WELLNESS

`WellnessDaily` is now keyed by `(athlete_id, date, source)`. Records from `source_a` and `source_b` for the same day are stored independently. This is tested in `test_multi_source_wellness_does_not_overwrite`.

Design decision: one row per `(athlete, date, source)` rather than a child `WellnessSource` table. This is the minimal change compatible with the existing model and it preserves multi-source semantics.

## 7. DEDUP_ENGINE

Implemented in `src/trailcoach/dedup/engine.py`.

- Scoring: `time_score`, `distance_score`, `duration_score`, `source_bonus`.
- Final score is a weighted sum of the four components.
- Decisions: `AUTO_LINK`, `REVIEW`, `SEPARATE`, `REIMPORT`.
- Ambiguous matches are persisted as `DedupeReview` rows with `final_score` and `candidates` JSON.
- Thresholds are configurable (`auto_link_threshold` default 0.85, `review_threshold` default 0.70).
- `SourcePriority` is read per `(athlete, metric)` and used to compute `source_bonus` (+0.10 for higher-priority new source, -0.05 for lower-priority, 0 for same/unknown).

Tests cover all decision branches and individual score validation.

## 8. PROVENANCE

Implemented in `src/trailcoach/provenance.py`.

`DataLineage` is a serializable dataclass that captures:

- `source`
- `timestamp`
- `source_record_id`
- `raw_file_id`
- `device_id`
- `account_id`
- `metric`
- `value_type` (`native`/`derived`/`estimated`/`unavailable`)
- `confidence`
- `data_quality`
- `quality_flags`

`Activity` and `WellnessDaily` now have a `provenance` JSON column. All foreign-key references are optional because not every source can provide raw files, devices or account records.

## 9. RAW_DATA_FIRST

Documented in `docs/architecture.md`:

```text
Raw source data
      ↓
immutable / raw representation  (RawFile)
      ↓
source-specific representation  (SourceActivity, WellnessDaily per source)
      ↓
canonical athlete model         (Activity, AthleteStateSnapshot)
      ↓
derived metrics
```

`RawStore` already implements content-addressable, immutable storage. Tests confirm that a duplicate SHA256 returns the existing `RawFile` row without overwriting the on-disk content.

## 11. ARCHITECTURE_FINDINGS

1. **No production migration mechanism**
   - Status: ARCHITECTURE_FINDING
   - The project uses `Base.metadata.create_all` and there is no Alembic setup.
   - Impact: every schema change relies on recreating the database or manual migration. This is acceptable for P0.0 but must be resolved before production use with real data.
   - Recommendation: add Alembic or an equivalent migration runner before P1.0.

2. **SourceState duplication**
   - Status: ARCHITECTURE_FINDING
   - `SourceState` was refactored to `(athlete_id, source)` but fields overlap with `AthleteSourceAccount`.
   - Impact: `SourceState` may be removed in a future migration; `AthleteSourceAccount` is the canonical source state table.
   - Recommendation: deprecate `SourceState` and remove once all consumers migrate.

3. **WellnessDaily source dimension**
   - Status: DESIGN_DECISION (not a finding)
   - Chose to extend `WellnessDaily` with `source` as part of the PK instead of a separate `WellnessSource` child table. This is the smallest safe change and supports multi-source ingestion.

## 12. DESIGN_DECISIONS

- Provider contract returns detached model instances (`ImportResult`) instead of writing to the DB. This keeps providers testable and source-agnostic.
- `DedupeEngine` returns actions rather than mutating the database directly, so the orchestrator controls transactions and side effects.
- `MetricCapability` stores `availability` as a free-text discriminator (`native`/`derived`/`estimated`/`unavailable`) without Garmin-specific values.
- Generic fixture names (`source_a`, `source_b`, `mock`) are used everywhere to avoid provider bias.
